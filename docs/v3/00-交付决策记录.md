## D1. hosted tools 双轨口径 —— 采纳

采纳产品经理提出的「协议兼容性 100% 交付 / 能力可用性由原生上游提供」拆分，及配套五道闸门。

**判定理由**：文档 §4.2.1 明确给出优先级「原生直通 > 本地完整模拟 > 可证明等价转换」，并禁止「静默降级、伪造成功」。它约束的是**语义不得丢失**，而非要求网关自建 Code Interpreter 沙箱与 Computer use VM。五道闸门中的第 4 条（无能力时返回标准错误，绝不丢掉 tool 后返回一个正常文本回答）正是「不静默丢失语义」的实现载体。

**Remote MCP 判定为完整实现**：采纳。它是 7 类 hosted tool 中唯一的纯网络协议能力，无沙箱/VM/GPU 依赖，且能让用户自行接入搜索、代码执行、向量库，反向补齐其他能力。

**验收口径**（§16 第 15 条改为双轨，两轨均为 NO-GO 项）：
- 轨道 A 直通轨：配置原生 Responses 上游时，7 类 hosted tool 端到端可用
- 轨道 B 无执行器轨：返回标准错误 + 启动期能力缺口告警 + 不伪造成功
- 轨道 C 本地执行器轨：不在本次交付，列入 v3.1

### D3.1 Q10 否决理由（默认开启 v3）

产品经理建议本次交付默认 `enabled: false`，理由是「让 v3 可先合入 main 不影响存量用户」。**否决。**

代码审计已证实：**现有 Responses 链路本身就是坏的**，不存在「保护存量可用状态」这一前提。

- `handler.py:949` 访问 `stream_translator.state`，而 `ResponsesStreamTranslator` / `CompositeStreamTranslator` 均无此属性 → 上游断流时抛 `AttributeError` → 客户端永远收不到 `response.completed` / `[DONE]` → Codex 挂死
- `CompositeStreamTranslator.finish_safely()`（`responses.py:634-640`）对 async `feed()` 返回的 coroutine 调 `extend()` 抛 `TypeError`，且边遍历 `out` 边向 `out` 追加造成死循环 → Anthropic 上游 + Responses 入站的流式收尾 100% 崩溃
- 生产路径首 token 超时实测 30 秒，深度推理模型必然被打断重放

默认关闭等于让用户继续留在一个确定有致命缺陷的实现上。

**裁定**：
- `responses_bridge.enabled` 默认 **`true`**，作用域**仅** `inbound_protocol == "responses"`
- Chat→Chat、Chat↔Anthropic 两条旧链路**完全不受影响**，这是 D4 的硬约束
- 保留秒级回滚：配置 `enabled: false` 或环境变量 `RESPONSES_BRIDGE_V3=false` 立即回退旧实现
- 优先级：env > YAML > 默认值
- 回滚方式必须写进交付说明

## D4. 改动隔离硬约束（不可协商）

审计确认三条链路当前共用 `ProxyHandler.__call__`（`handler.py:347-717`），`server.py:75` 注册的是 `add_route("*", "/v1/{tail:.*}")` 通配路由。v3 必须在此基础上建立清晰边界：

```python
if inbound_protocol == "responses" and v3_enabled:
    return await handle_responses_v3(...)
return await handle_legacy_protocol(...)
```

- v3 的 RequestSanitizer、reasoning 丢弃、参数 allowlist、output index 分配、Responses SSE 状态机**只允许**在 responses 分支执行
- 不得全局删除旧 Chat 请求中的 `reasoning_content`
- Responses 参数 allowlist 不得应用于 `/v1/chat/completions` 与 `/v1/messages`
- call ID 归一化不得改写旧 Chat 客户端的原始 call ID
- heartbeat 只写入 Responses SSE 流
- 保留 `ResponsesStreamTranslator` / `StreamO2A` / `StreamA2O` 既有外部接口签名

**回归基线：179 个测试全绿**（`.venv3`，已实测）。任一旧协议测试失败 = v3 NO-GO。

## D7. 架构师待裁决点回复（U7 / U4）

### D7.1 U7 —— reasoning item 的「不透明标识」存什么

**裁定：只存引用与元数据，永不存密文本体，永不回放。**

| 项 | 规定 |
|---|---|
| 落库内容 | `item_id`、`type="reasoning"`、`output_index`、`created_at`、`content_sha256`（对上游 reasoning 原文做 SHA-256，仅用于去重/审计对账）、`token_count`（若上游提供）、`summary_present: bool` |
| 禁止落库 | reasoning 明文、`encrypted_content` 密文本体、`reasoning_content`、`thinking` 块、任何可还原推理过程的字段 |
| `GET /v1/responses/{id}` 返回 | reasoning item **占位对象**：`{"id": ..., "type": "reasoning", "summary": [], "content": []}`，不含 `encrypted_content` |
| 下一轮请求 | 无论客户端是否回传 reasoning item，`RequestSanitizer` 一律丢弃（铁律 1） |
| 客户端要求回放时 | 返回官方错误 `unsupported_parameter`，`param="include[]=reasoning.encrypted_content"`，**不静默降级** |

**依据**：铁律 1（reasoning 只出不进）为最高优先级，冲突时铁律胜出。回放能力（`include: ["reasoning.encrypted_content"]`）明确划入 **v3.1 范围外**，在 T38 兼容报告中以「本次不交付（v3.1）」标注 —— 不得写「部分支持」。

**影响任务**：T10（item registry 的 reasoning `redact`）、T20（验收项⑤查库断言 reasoning 文本列为空）、T22（验收项⑤）、T38（兼容报告条目）。
